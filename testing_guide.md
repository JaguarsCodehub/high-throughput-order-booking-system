# End-to-End Testing Guide: Order Booking System

This guide outlines the exact steps to set up your Supabase database, run Kafka, launch the microservices, and execute test API requests to observe the event-driven Saga pattern in action.

---

## Phase 1: Set up the Database (Supabase)

Since you are using Supabase, you do not need to host PostgreSQL locally via Docker. 

### Step 1.1: Run the Database Schema
1. Log in to your **Supabase Dashboard** and navigate to your project.
2. Click on the **SQL Editor** in the left sidebar.
3. Click **New Query**.
4. Copy the entire contents of your local `sql/init.sql` file and paste it into the editor.
5. Click **Run**. You should see a success message indicating the enums and tables were created.

### Step 1.2: Insert Seed Data
To test placing an order, we need at least one user and one product (with stock in the inventory table) already in the database. Run this script in the Supabase SQL Editor:

```sql
-- 1. Insert a test user (Save the ID returned!)
INSERT INTO users (email, phone, full_name)
VALUES ('testuser@example.com', '+1234567890', 'John Doe')
RETURNING id;

-- 2. Insert a test product (Save the ID returned!)
INSERT INTO products (name, description, price, sku)
VALUES ('PlayStation 5', 'Next-gen gaming console', 499.99, 'PS5-001')
RETURNING id;

-- 3. Add inventory for the product (Replace <PRODUCT_ID> with the ID returned above)
-- We will start with a physical stock of 10 items
INSERT INTO inventory (product_id, quantity, reserved)
VALUES ('<PRODUCT_ID>', 10, 0);
```

> [!IMPORTANT]
> Make a note of the **User ID** and **Product ID** generated by the `RETURNING` statements. You will need them to construct your API requests.

## Phase 2: Configuration (`.env`)

Create a `.env` file in the root directory of your project (`e:\Projects\order-booking-system\.env`) and populate it with your Supabase credentials and Kafka broker address:

```env
# Database Configuration (Use your Supabase connection string)
# If direct IPv6 fails, select the "Session Pooler" option in Supabase
DATABASE_URL="postgresql://postgres.[your-project-id]:[password]@aws-0-region.pooler.supabase.com:6543/postgres"

# Kafka Configuration
KAFKA_BROKERS="localhost:9092"

# Service Ports
ORDER_SERVICE_PORT=3001
```

## Phase 3: Start Kafka & Provision Topics

### Step 3.1: Start Kafka Infrastructure
Run the following command in your terminal to start ZooKeeper, Kafka, and the Confluent Control Center UI:
```powershell
docker-compose up -d
```

### Step 3.2: Create Kafka Topics Programmatically
Since you are on Windows, executing the bash script might require Git Bash. Instead, you can run our Node.js Admin script directly:
```powershell
npx ts-node src/kafka/admin.ts
```
*Expected Output:*
```
Connecting Admin...
Admin connected successfully!
Existing topics: []
Creating topics: [ 'order.created', 'inventory.reserved', 'inventory.failed', 'payment.processed', 'payment.failed' ]
Topics created successfully!
Admin disconnected.
```

### Step 3.3: Verify via Kafka UI
Open your browser and navigate to:
👉 **[http://localhost:9021](http://localhost:9021)** (Confluent Control Center)

From here, you can click on your cluster and select **Topics** on the sidebar to verify that all 5 topics have been successfully created.

## Phase 5: Trigger & Test the Workflows

You can use Postman, Insomnia, or simple `curl` commands in a terminal to send requests.

### Test Scenario A: The Happy Path (Successful Order & Payment)
Replace `<USER_ID>` and `<PRODUCT_ID>` with the actual UUIDs you got in Step 1.2.

**Request:**
* **Method:** `POST`
* **URL:** `http://localhost:3001/api/orders`
* **Headers:**
  * `Content-Type: application/json`
  * `x-idempotency-key: unique-key-happy-path-01`
* **Body:**
```json
{
  "userId": "<USER_ID>",
  "totalAmount": 499.99,
  "items": [
    {
      "productId": "<PRODUCT_ID>",
      "quantity": 1,
      "unitPrice": 499.99
    }
  ]
}
```

**What you will see in the terminals:**
1. **Order Service:** Receives the request, writes `orders` and `order_items` to Supabase, and publishes `order.created`.
2. **Inventory Service:** Receives `order.created`, updates `reserved` in Supabase to `1` (leaving `available` as `9`), and publishes `inventory.reserved`.
3. **Payment Service:** Receives `inventory.reserved`, mock charges the client (90% success rate), marks the order as `confirmed` in DB, and publishes `payment.processed`.
4. **Notification Service:** Receives `payment.processed` and prints a console log simulating sending a success email to the user.

---

### Test Scenario B: Idempotency Prevention (Re-submitting Same Request)
Send the exact same request again with the **same** header:
`x-idempotency-key: unique-key-happy-path-01`

**Expected Response:**
* **Status:** `409 Conflict`
* **Body:** `{ "error": "Order with this idempotency key already exists" }`
* *No additional database writes or Kafka events are produced!*

---

### Test Scenario C: Out of Stock (Saga Failure Compensation)
Repeatedly buy items (or place a single order requesting `20` units of your product when you only have `10` in stock).

**Request Body (Requesting 20 items):**
```json
{
  "userId": "<USER_ID>",
  "totalAmount": 9999.80,
  "items": [
    {
      "productId": "<PRODUCT_ID>",
      "quantity": 20,
      "unitPrice": 499.99
    }
  ]
}
```

**What you will see in the terminals:**
1. **Order Service:** Places order as pending and publishes `order.created`.
2. **Inventory Service:** Receives event, runs the SQL query, realizes `quantity (10) - reserved (0) < requested (20)`. It rolls back the transaction and publishes `inventory.failed`.
3. *(The order remains pending or gets cancelled in the DB depending on if you configure a listener for inventory.failed)*.

---

### Test Scenario D: Payment Failure (Saga Rollback / Stock Release)
Because our mock payment fails 10% of the time, keep placing successful orders using **new idempotency keys** until you hit a mock payment failure.

**What you will see in the terminals when the payment fails:**
1. **Order Service:** Publishes `order.created`.
2. **Inventory Service:** Successfully reserves 1 item (`reserved` goes up by 1) and publishes `inventory.reserved`.
3. **Payment Service:** Simulates payment failure. It updates the database order status to `cancelled` and publishes `payment.failed`.
4. **Inventory Service:** Receives `payment.failed`, performs a **compensating transaction** to release the hold (`UPDATE inventory SET reserved = reserved - 1`), returning the item back to the market!
5. **Notification Service:** Receives `payment.failed` and prints a console log simulating a failure email to the user.
